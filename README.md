# FitLog · 6단계

한국어 개인 건강 관리 웹앱입니다. 기존 계정·설정·식단·웨이트 기록과 루틴을 유지하며 **휴식 타이머, 바코드 입력, 기간별 CSV/Excel, 백업·복구와 계정 관리**를 제공합니다. 임의의 음식·운동·측정 데이터는 제공하지 않습니다.

## 시작

Node.js 22 이상을 사용하세요. 이 환경에서는 Node.js 24.19.0으로 검증했습니다.

```sh
npm ci --cache /tmp/fitlog-npm-cache
cp .env.example .env.local
# .env.local에 프로젝트 URL과 publishable key를 입력
npm run dev
```

Supabase 환경변수가 없으면 앱은 **미연결 빈 상태 미리보기**로 실행됩니다. 로그인·프로필 저장·비밀번호 저장은 비활성화됩니다. 실제 데이터와 데모 데이터를 혼합하지 않으며 데모 계정도 제공하지 않습니다.

운영 빌드:

```sh
npm run build
npm run start
```

`NEXT_PUBLIC_*` 값을 변경하면 개발 서버를 재시작하고 운영 빌드는 다시 생성하세요. `NEXT_PUBLIC_APP_NAME`으로 프로젝트 표시 이름을 변경할 수 있습니다. URL과 publishable/anon 키만 앱에 전달합니다. service-role 키는 앱 환경변수로 설정하지 않습니다.

## Supabase 프로젝트 연결과 최초 관리자

1. Supabase 프로젝트를 생성합니다.
2. 새 프로젝트는 `supabase/migrations/`의 SQL을 파일명 순서대로 각각 한 번 적용합니다. 기존 프로젝트는 아직 적용하지 않은 SQL만 순서대로 추가합니다. **5단계까지 적용한 프로젝트는 202610140005_service.sql만** 추가 적용합니다. 4단계라면 analysis → service, 3단계라면 wellness → analysis → service, 2단계라면 workout → wellness → analysis → service, 1단계라면 diet → workout → wellness → analysis → service 순서입니다. 기존 테이블을 삭제하거나 초기화하지 않습니다. 이미 적용한 SQL을 다시 실행하지 않습니다. 기존 데이터는 먼저 백업하고 실제 프로젝트에서는 트랜잭션으로 마이그레이션을 적용하세요.
3. Auth 설정에서 **Allow new users to sign up을 끕니다**. 화면에 가입 버튼이 없다는 것만으로 가입을 차단할 수 없습니다. 로컬 설정은 `enable_signup = false`입니다.
4. Auth URL Configuration에 실제 서비스 주소를 Site URL로 등록하고 `/auth/confirm`, `/auth/callback`을 Redirect URLs에 추가합니다. 개발 환경은 개발 주소를 사용합니다.
5. Invite user 이메일 템플릿의 링크를 다음으로 설정합니다.

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite">계정 초대 수락</a>
```

비밀번호 복구 템플릿을 사용할 경우 동일한 URL에 `type=recovery`를 지정합니다. 복구 이메일 발송 UI는 이번 단계에 포함되지 않습니다.

6. Auth > Users에서 관리자 본인의 이메일만 초대합니다. 초대 링크에서 비밀번호를 설정하고 로그인합니다. 이후 여러 사용자에게 개방할 때도 관리자가 초대할 수 있습니다. 관리자 역할·관리자 화면은 제공하지 않습니다. 공개 가입은 6단계의 명시적 설정과 운영 준비 후 활성화할 수 있습니다.
7. `.env.local`에 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 설정합니다. 프로젝트의 publishable key 또는 legacy anon key를 사용할 수 있습니다. 비밀키를 코드나 Git에 넣지 않습니다.
8. 네트워크 제한이 있는 클라우드 환경이라면 환경 설정에서 해당 프로젝트의 정확한 `<project-ref>.supabase.co` 호스트를 허용합니다.
9. 로그인, 프로필 저장, 로그아웃을 확인합니다. 다른 사용자의 접근은 아래 RLS 테스트로 확인합니다.

초대 이메일 전송에는 Supabase 프로젝트의 이메일 발송 설정이 필요합니다. 프로젝트를 아직 만들지 않았으므로 호스팅 프로젝트의 연결·메일 발송·배포는 별도로 확인해야 합니다.

## 1단계 기반 (유지)

- 이메일/비밀번호 로그인, POST 로그아웃, 로그인 검증과 개인 페이지 보호
- Supabase SSR 쿠키 세션 및 요청 시 토큰 갱신. 서버의 `getUser()`로 사용자 검증
- 관리자 초대/복구 링크 처리, 비밀번호 설정·변경
- 프로필 이름, IANA 시간대, 체중·신장 기본 단위 저장, Zod 입력 검증
- 사용자 시간대 기반 홈 날짜 표시
- 한국어 홈/식단/운동/캘린더/분석/설정, PC 사이드 메뉴와 모바일 하단 메뉴
- 라이트·다크·시스템 테마, 기기별 선택 유지
- PWA manifest, 192/512 PNG 아이콘, 서비스 워커 등록. 개인정보/인증 페이지를 캐시하지 않음
- 기록 테이블별 RLS, 소유자 참조를 확인하는 복합 외래키

PWA는 설치 가능한 기본 구조입니다. 운동 입력 중 연결이 끊기면 이미 열린 화면의 임시 입력 복구와 연결 복구 시 저장 재시도를 제공합니다. 전체 페이지의 오프라인 실행, 백그라운드 동기화·푸시 알림은 구현하지 않았습니다. 실제 기기별 설치 동작은 HTTPS 배포 후 확인해야 합니다. Recharts로 실제 체성분·영양·운동 기록의 그래프를 표시합니다. 탄단지 비율은 실제 식단의 4/4/9 환산 열량으로 표시합니다.

## 2단계 식단·영양 관리

- 아침·점심·저녁·간식, 날짜별 조회·섭취량 수정·음식 기록 삭제
- 저장된 개인 음식의 이름/브랜드 검색, 영구 즐겨찾기, 음식 직접 등록 및 등록 정보 수정
- 제품 1개/1회 제공량의 실제 g와 표시값 → 100g 기준 환산 → 섭취량에 따른 자동 계산
- 열량·탄수화물·단백질·지방·총 중량 합계, 사용자 입력 일일 목표·달성률·남은 양·초과량
- 자주 먹는 음식/중량 목록을 식단 조합으로 저장·삭제하고 원하는 식사에 적용
- 다른 날짜의 전체 식단 복사. 대상 날짜의 기존 기록에 **추가**되며 반복 복사는 중복 기록이 됩니다. UI에서 확인 후 실행합니다.

음식은 사용자 직접 등록 데이터입니다. 제조사/브랜드와 제품 영양표·자료 이름/링크를 출처로 입력해야 합니다. 식약처 공식 데이터 제공 사이트는 현재 환경에서 CONNECT 403으로 차단되었고 API 키도 없습니다. 공식 문서를 확인할 수 없어 API 연동을 추측 구현하지 않았습니다. 독립적으로 검증한 기본 음식 데이터도 제공하지 않습니다. 실제 등록한 음식만 검색·기록할 수 있으며, 테스트용 값은 격리 테스트 DB에서만 사용하고 삭제합니다.

신규 음식은 100g 영양값과 원본 표시 기준 중량을 저장합니다. 예를 들어 150g 제품의 표시값이 195kcal이면 100g당 130kcal, 300g 섭취 시 390kcal입니다. 중량을 모르면 개수/제공량을 g로 환산할 수 없으므로 실제 g 입력이 필요합니다. 서버와 DB에서 입력을 검증하고 DB의 `numeric` 계산을 저장합니다. 합계 계산 전에 반올림하지 않으며 화면만 소수 첫째 자리까지 표시합니다. 탄단지 비율은 4/4/9 열량 합계의 비율로, 실제 표시 kcal 합계와 별개입니다.

**기록 날짜:** `meal_date`에 YYYY-MM-DD를 저장합니다. 첫 식단 진입은 한국 기준 오늘 날짜를 명시한 URL로 이동합니다. 자정을 지나도 선택한 URL 날짜와 저장 날짜가 유지되며 기기의 시간대/사용자 프로필 시간대와 무관합니다. 기존 `eaten_at`은 유지하고 마이그레이션에서 한국 날짜를 채웁니다.

**과거 기록 보존:** 기록 당시 음식명·브랜드·출처·100g 영양값을 별도로 저장합니다. 음식 정보 수정은 과거 식단을 바꾸지 않습니다. 기록 중량 수정과 날짜 복사는 저장된 스냅샷으로 계산합니다. 저장한 조합을 새로 적용할 때는 현재 음식 정보로 계산합니다. 식단 화면의 일일 목표는 현재 사용자 설정입니다. 5단계 분석은 변경일부터 저장된 목표 이력을 사용해 과거 섭취량과 비교합니다.

식단 추가·중량 수정·삭제·조합 저장·날짜 복사는 RLS를 유지하는 `security invoker` RPC입니다. 여러 음식 중 하나가 유효하지 않거나 다른 사용자 음식이면 전체 요청을 롤백합니다. 사용자 ID는 인증 세션에서 정하며 임의 사용자 ID를 폼에서 받지 않습니다. DB 조회 실패는 빈 식단으로 표시하지 않습니다.

```sh
npm run test:unit  # 계산, 제공량 환산, 잘못된 값, 한국 자정/윤년
npm run test:local # DB 마이그레이션, RLS, 기존 로그인 + 식단 통합 테스트
```

## 3단계 운동·루틴 관리

- 날짜별 운동 생성·조회·수정·삭제, 종목 직접 등록 및 운동명/부위 검색
- 세트마다 중량(kg)·반복·5가지 세트 종류·RPE 또는 RIR·휴식(초)·완료 체크
- 모바일 숫자 키보드, 중량 ±2.5kg·반복 ±1 버튼, 세트 추가·복제·삭제, 종목 순서 변경
- 종목 선택 시 가장 최근 완료 기록 표시, 지난 세트 복사, 사용자 편집 목표 중량·반복·세트 수
- 이전 동일 종류 세트 대비 중량 증가 또는 같은 중량에서 반복 증가 표시
- 전체/종목별 메모, 입력 중 자동 저장, 새로고침 후 기록 유지, 다중 기기 버전 충돌 선택
- 1~60일 루틴 생성·수정·삭제·활성화, 사용자 요청의 8일 부위/휴식 초안 제공. 저장하기 전에는 활성 루틴으로 표시하지 않음
- 일차별 운동·목표·순서 편집, 완료 후 다음 일차 이동, 휴식일 완료·건너뛰기·같은 순서로 다음날 연기, 변경 이력

**날짜와 순환:** 운동도 한국 기준의 고정 `session_date`를 사용합니다. 기록 당시 루틴 일차·이름·목표와 활성화별 `run_id`를 저장합니다. 일정 연기는 해당 일차를 다음 날짜로 이월하며 이미 수행한 기록 날짜는 바꾸지 않습니다. 완료한 운동과 다음 일차 이동은 별도 작업입니다. 빈 운동 또는 미완료 세트가 있으면 운동 완료를 거부합니다. 루틴 변경·삭제는 이전 수행 기록을 삭제하지 않습니다.

**개인 기록:** 완료한 운동의 완료된 본세트(워밍업 제외)로 최고 중량·최고 반복·추정 1RM을 DB에 계산해 저장합니다. Epley `중량 × (1 + 반복/30)`은 2~10회에만 적용하고 1회는 실제 중량을 사용합니다. 0kg 또는 11회 이상은 1RM 추정에서 제외합니다. 최고 중량과 최고 반복은 서로 다른 세트의 기록일 수 있습니다. 기록 수정·삭제 시 다시 계산하며 사용자가 PR 테이블을 직접 수정할 수 없습니다. 추정치는 실제 1RM과 다를 수 있습니다.

**자동 저장:** 숫자 입력은 600ms 후, 선택·완료 체크는 즉시 서버 저장을 요청합니다. 같은 행은 순서대로 저장하며 DB 버전이 변경되면 HTTP 409 충돌을 표시하고 서버 값 사용/내 입력 재저장 중 선택합니다. DB 저장 대기·오류를 완료로 표시하지 않으며 대기 중 기록 삭제·일정 이동·운동 완료를 막습니다. 미전송 입력은 사용자 ID/행 ID별 `localStorage`에 보관하고 서버 저장 성공 후 제거합니다. 공유 기기에서는 로그아웃 후 사이트 데이터도 지우세요. 임시 저장은 서버 백업이나 전체 오프라인 기능이 아니며 브라우저 데이터 삭제 시 사라집니다.

새 테이블에 RLS와 소유자 복합 외래키를 적용하고 변경 RPC는 인증 사용자만 실행할 수 있습니다. 저장 버전 충돌·사용자 간 참조·PR 위조·권한 우회 차단을 실제 로컬 REST로 검사합니다. 기존 운동 세트의 중량·반복·메모와 한국 날짜, 루틴 항목, PR 백필 보존도 마이그레이션 테스트에 포함합니다.

## 4단계 캘린더·체성분·컨디션

- 월간 7열·42칸 캘린더, 월 이동·날짜 직접 선택·오늘 이동, 한국 기준 고정 날짜
- 운동 완료(파랑), 운동 중(주황), 완료한 루틴 휴식(초록), 현재 일정의 휴식 예정(빈 원), 식단·체성분·컨디션 표시
- 선택 날짜의 식단/영양 합계·운동 종목/개별 세트·체성분·컨디션 통합 조회
- 과거 날짜를 전달하는 식단·운동 입력 링크와 체성분/컨디션 저장·수정·삭제
- 체중·골격근량·체지방률·체지방량·허리둘레·측정 메모; 미측정 항목은 null
- 체지방량 직접 측정 또는 체중×체지방률 계산 선택, 실측/계산 출처 표시 및 DB에서 계산 검증
- 선택 입력 수면(0~24시간), 피로/만족(1~5), 통증 부위·강도(0~10), 자유 메모. 0과 미입력을 구분
- 분석 페이지의 실제 Recharts 일별/주간 체중·골격근량·체지방률 그래프, 7/30/90일·전체와 종료일 선택, 항목별 처음/마지막 비교

**날짜·과거 데이터:** `body_measurements.measured_date`와 `condition_records.recorded_on`은 고정 YYYY-MM-DD입니다. 기존 측정 시각은 한국 날짜로 백필하고 신장·근육·체중·체지방률과 컨디션 활력/기분은 유지합니다. 같은 날짜의 기존 복수 측정도 삭제하거나 합치지 않습니다. 새 측정 추가와 기존 측정 수정을 구분합니다. 다른 달의 칸은 선택한 뒤 그 달 기록을 조회합니다.

**측정 출처:** `fat_mass_source`가 measured이면 입력한 실제 값, calculated이면 DB의 체중×체지방률/100 계산값입니다. 계산을 명시적으로 선택했을 때만 저장하며, 출처 없는 체지방량이나 필요한 값이 없는 계산은 거부합니다. 계산값을 직접 측정으로 전환하면 실제 값을 다시 입력합니다. 측정하지 않은 체지방량을 임의로 채우지 않습니다.

**그래프 기준:** 같은 날 복수 측정이면 최근 등록 측정 하나를 사용합니다(created_at, 측정 시각, ID 순). 해당 기록의 빈 항목을 이전 측정에서 가져오지 않습니다. 기간은 종료일 포함 7/30/90일 또는 종료일까지 전체입니다. 일별 그래프는 미측정 날짜를 null로 두고 선을 연결하지 않습니다. 주간 체중 평균은 월~일 중 선택 기간 내 실제 체중 측정일만 계산하고 부분 주의 측정일 수도 표시합니다. 빈 주는 평균을 만들지 않습니다. 비교 표는 항목별 실제 첫/마지막 측정이며 두 날짜 이상 있을 때만 변화가 표시됩니다. 체지방률 변화의 단위는 %p입니다. 표의 체지방량 출처도 구분합니다. 표시값만 소수 첫째 자리로 반올림합니다.

**저장·권한:** 기존 체성분/컨디션 테이블의 RLS를 유지하며 변경과 집계 RPC는 security invoker입니다. UUID를 알더라도 타 사용자 기록을 읽거나 변경할 수 없습니다. 수정·삭제는 버전 일치 시만 실행하고 충돌하면 최신 기록을 불러오도록 안내합니다. 월 집계는 DB에서 수행하고 전체 체성분 그래프는 JSON 집계 RPC로 조회해 기본 REST 1,000행 제한에 의해 잘리지 않게 했습니다. 조회 오류를 빈 기록으로 표시하지 않습니다. 체성분·컨디션은 명시적으로 저장하며 운동 자동 저장과 별개입니다.

```sh
npm run test:unit
npm run test:local -- tests/wellness.spec.ts  # 새 기능만 PC/모바일 검증
npm run test:local                           # 1~4단계 전체 회귀
```

체성분 분석은 기본 탭으로 유지하며 5단계에서 영양·운동 분석 탭을 추가했습니다. 자동 건강 판단·처방·통증 진단은 제공하지 않습니다. 실제 기기의 키보드/터치/PWA 동작은 HTTPS 배포 후 추가 확인이 필요합니다.

## 5단계 목표·영양·운동 성장 분석

- 벌크업·다이어트·체중 유지·직접 설정, 현재/목표 체중·선택 목표 날짜·활동 수준·하루 열량/탄단지 목표 저장·수정
- 홈과 분석의 목표 설정은 기존 식단의 `nutrition_goals`를 공유합니다. 활동 수준은 저장만 하고 필요 열량/TDEE나 영양 처방을 자동 생성하지 않습니다. 현재 체중 입력은 체성분 측정 기록을 바꾸지 않습니다.
- 분석: 기존 체성분 탭 + 영양 분석 + 운동 성장. 7/30/90일·전체와 한국 기준 종료일, 종목 필터
- 영양 기록일 평균·주간 평균, 탄단지 추이, 당시 목표 대비 실제 섭취·달성 일수, 주간 체중/섭취 열량 비교
- 종목별 최고 중량·반복·추정 1RM, 일별 성장/운동량 그래프, 기간 첫/최근 날짜 비교, 주간 수행일/세션/본세트/운동량, 부위별 본세트, 개인 최고 갱신
- 홈: 오늘 열량/탄단지 달성률과 남은 양/초과량, 최근 30일 최신 측정 체중·최근 7일 변화, 운동 성장·개인 기록, 최근 7일 기록 요약

**목표 이력·과거 날짜:** 목표 변경은 서버 한국 날짜부터 적용하며 같은 날짜는 마지막 저장 목표를 사용합니다. 일반 사용자는 `nutrition_goal_history`를 조회만 할 수 있고 DB 트리거만 이력을 작성합니다. 2~4단계 목표 변경 이력은 없었으므로 이전 목표를 추측하지 않습니다. 기존 목표는 마지막 `updated_at`의 한국 날짜부터만 백필하고 이전 날짜의 목표는 미상으로 표시합니다. 기존 일반 `goals` 데이터도 삭제하지 않습니다. 식단 화면은 이전과 같이 현재 목표를 표시하며, 과거 분석만 당시 목표를 사용합니다. 목표 저장은 버전이 일치해야 하며 충돌 시 최신 목표를 불러와 다시 편집합니다. 기존 식단에서 목표를 바꿔도 새 메타데이터를 유지하고 버전·이력이 함께 갱신됩니다.

**영양 계산 기준:** 음식 항목이 있는 날짜별 저장 영양 스냅샷을 합산합니다. 기록일 평균 = 해당 날짜 합계의 합 / 식단 기록일 수. 미기록 날짜와 빈 식사는 분모에서 제외하며 실제 0kcal 음식 기록일은 포함합니다. 일부 식사만 기록했을 수도 있으므로 완전한 하루 섭취량이라고 단정하지 않습니다. 전체 목표 달성 일수는 당시 알려진 활성 목표의 설정 항목 모두가 90~110%인 날 수이며, 별도로 열량만 같은 범위인 날 수를 표시합니다. 당시 목표가 없거나 비활성인 날은 평가 분모에서 제외합니다. 달성률 = 실제 / 목표 ×100, 100% 이상도 수치와 초과량을 표시합니다. 탄단지 열량 환산 4/4/9와 제품 표시 열량은 다를 수 있으며 분석 kcal는 실제 저장된 표시 열량 기준입니다.

**주간·체중 비교:** 월~일 중 선택 기간 안의 실제 기록만 포함합니다. 첫/마지막 부분 주를 7일로 환산하지 않습니다. 체중 평균은 해당 기간의 체중 측정일 수, 열량 평균은 식단 기록일 수를 각각 분모로 사용하고 두 분모를 표에 표시합니다. 체중은 4단계와 같이 하루 최근 등록 측정 하나만 사용합니다. 미측정일·빈 주를 0 또는 이전 값으로 채우지 않고 그래프도 결측을 연결하지 않습니다. 전주 차이는 바로 이전 주와 모두 체중 평균이 있는 경우만 표시합니다.

**운동 계산 기준:** 완료된 세션의 완료된 유효 본세트(탑·백오프·일반·드롭)만 집계합니다. 워밍업·미완료 세션/세트·중량 또는 반복이 없는 기록은 제외합니다. 운동량 = Σ(외부 중량 kg × 반복), 체중 운동의 자체 체중은 포함하지 않습니다. 0kg 세트는 본세트 수·수행 빈도에 포함되지만 운동량은 0입니다. 운동일은 서로 다른 기록 날짜 수이며 같은 날 두 세션은 1일/2세션입니다. 부위는 기록 당시 부위명 기준이며 복합 부위명을 여러 범주로 중복 계산하지 않습니다. 최고 중량·최고 반복·최고 추정 1RM은 서로 다른 세트에서 나올 수 있으므로 가짜 중량×반복 조합으로 표시하지 않습니다.

**추정 1RM·개인 기록:** Epley 중량×(1+반복/30)을 2~10회에 적용하며 1회는 기록 중량, 0kg 또는 11회 이상은 미추정입니다. 실제 1RM과 다를 수 있습니다. 선택 기간 최고와 종료일까지 전체 최고(이전 기간 포함)를 구분합니다. 개인 최고 갱신은 종료일까지의 과거 완료 기록과 비교하며 첫 기록은 비교 없는 기준 기록으로 표시합니다. 최근/과거 비교는 선택 기간의 첫/마지막 기록 날짜 요약입니다. 기록 수정·삭제는 저장값에 근거해 분석에 반영됩니다.

**개인 목표 참고 분석:** 종료일까지 최근 두 7일 구간의 평균 체중과 당시 열량 목표 대비 섭취량을 비교합니다. 각 구간 체중 3일 이상, 목표와 비교 가능한 식단 10일/14일 이상, 14일 동안 동일한 목표 유형·열량이 있는 경우에만 조건부 계획 검토 문구를 제공합니다. 선택 기간 밖의 기록은 사용하지 않으므로 7일 필터에서는 14일 조건이 충족되지 않습니다. 0.2kg 미만 평균 차이는 표시용 작은 변화 기준이며 정체나 인과관계를 확정하지 않습니다. 기록이 부족하거나 목표가 변경되면 조절 방향을 제안하지 않고 자료를 더 확인하도록 안내합니다. 단기간 변화, 수분·누락 기록 등의 영향은 분리할 수 없습니다.

**조회·보안:** 집계 RPC는 인증 사용자 소유 데이터만 조회하는 `security invoker`입니다. 다른 사용자 종목 ID와 익명 호출을 거부하고 새 목표 이력에도 RLS를 적용했습니다. 기간 전체 영양·체성분·운동은 DB JSON 집계로 기본 REST 1,000행 제한에 잘리지 않습니다. 그래프는 선택 기간 전체, 영양 날짜 표는 최근 100개 기록일, 개인 최고 목록은 최근 10건, 홈 개인 기록은 5건을 표시합니다. 조회 실패를 빈 데이터로 표현하지 않습니다. 기존 식단·운동·체성분 저장 후 홈/분석 캐시도 갱신합니다.

```sh
npm run test:unit
npm run test:local -- tests/analysis.spec.ts  # 5단계 PC/모바일·실제 REST 검증
npm run test:local                           # 1~5단계 전체 회귀
npm run typecheck
npm run build
npm run test:e2e
```

구현 구조: `src/lib/analysis/model.ts`에 계산·검증·결측 처리, `src/components/analysis/`에 목표/영양/운동/홈 화면, `src/app/(app)/analytics/actions.ts`에 인증된 목표 저장, `supabase/migrations/202610140004_analysis.sql`에 확장·목표 이력·집계 RPC를 배치했습니다. 실제 테스트 결과와 남은 외부 검증은 `VALIDATION.md`에 기록합니다.


## 6단계 편의·데이터 관리·공개 전환 준비

**실제로 동작하는 기능:** 종목별 기본 휴식, DB 세트 완료 저장 후 자동 타이머, 남은 시간·일시정지·계속·초기화·수동 시작, 종료 알림, 내 음식 바코드 카메라/사진/번호 검색과 직접 등록, CSV/Excel 기간 내보내기, JSON 전체 백업/복구, 내 기록 전체 삭제·회원 탈퇴, 공개 가입 설정, 설치 안내·연결/로딩/오류 상태를 구현했습니다. 1~5단계의 로그인·프로필·식단·운동·루틴·캘린더·측정·목표·분석을 유지합니다.

**휴식 타이머:** 종목 기본 휴식은 DB에 저장합니다(0~3,600초, 빈 값 미설정). 세트에 휴식 값이 있으면 그 값이 우선하고 0초는 자동 시작하지 않습니다. 실제 완료 저장이 성공한 뒤 시작하며 기존 세트의 휴식 기록을 변경하지 않습니다. 기기/사용자별 종료 시각과 상태를 저장하고 재접속 시 시각 차이로 계산합니다. 시스템 알림은 사용자가 허용할 때만 보내고 소리도 선택적으로 켭니다. 동일 알림의 재전송을 막고 알림을 누르면 앱을 엽니다. 운동 화면 이동·백그라운드/화면 잠금/앱 종료에서는 정확한 시각 알림을 보장하지 않습니다. 서버 Push·예약 OS 알람은 제공하지 않습니다. 기기 시계 변경의 영향도 받을 수 있습니다.

**바코드:** EAN-8/UPC/EAN-13/GTIN-14 숫자와 검증 숫자를 검사합니다. 카메라 후면 우선, 기기에서 ZXing 판독, 종료/닫기 시 카메라 해제, 사진 판독과 번호 입력 대안을 제공합니다. HTTPS·브라우저 카메라 권한이 필요합니다. 개인 음식의 바코드부터 검색하고 사용자별 같은 바코드는 하나의 제품에 연결합니다. 검색 결과가 없으면 100g 기준 제품명·브랜드·열량·탄단지·출처를 직접 입력하고 중량을 확인한 뒤 제품/식단을 한 트랜잭션으로 저장합니다. 요청 UUID와 해시로 같은 저장 재시도를 중복 처리하지 않습니다.

**외부 바코드 DB:** Open Food Facts v3.6의 제품 조회 어댑터를 준비했으며 기본값은 `none`입니다. `FITLOG_BARCODE_PROVIDER=openfoodfacts`, `FITLOG_OFF_LICENSE_ACKNOWLEDGED=true`, 실제 `FITLOG_OFF_CONTACT`를 설정하기 전에 공식 이용약관·ODbL 적용·이용 신고를 확인해야 합니다. 공식 문서에서 DB ODbL-1.0, 개별 내용 DbCL-1.0, 제품 사진 CC BY-SA 3.0을 확인했으며 제품 사진은 사용하지 않습니다. 현재 제품 API/약관 사이트가 환경 네트워크 정책으로 차단되어 외부 실제 응답/전체 약관은 검증하지 않았습니다. `100g` 기준과 4개 영양값이 확인되는 경우만 미리 채우고 값 누락/100mL 기준은 빈 값으로 직접 확인하도록 처리합니다. 출처·라이선스를 유지하고 커뮤니티 자료의 정확성을 보장하지 않습니다.

**음식 사진:** OpenAI Responses 이미지/구조화 출력 계약의 서버 어댑터를 구현했습니다. 현재 키/모델이 없으므로 사용 불가 상태입니다. 서버 전용 `FITLOG_PHOTO_PROVIDER=openai`, `FITLOG_PHOTO_MODEL`, `FITLOG_PHOTO_API_KEY` 설정과 실제 연결 검증이 필요합니다. 사용자가 외부 전송에 동의한 뒤 JPEG/PNG/WebP 5MB·16MP까지 처리하고 1024px 재인코딩으로 메타데이터를 제거합니다. 사진은 앱 DB에 저장하지 않습니다. 음식·중량·조리 방식은 추정과 불확실성으로 표시하며 사용자가 수정/확인하고 등록 음식과 연결해야 저장됩니다. AI가 영양성분을 생성하지 않고 선택한 음식의 영양정보로 계산합니다. 확인 메모와 재시도 방지 UUID도 저장합니다. 키는 `NEXT_PUBLIC_*`에 넣지 않습니다. 제공처 보존/학습·국외 이전 조건은 별도 확인해야 합니다.

**내보내기·백업:** 설정에서 시작/종료 한국 날짜, 식단/운동/체성분, CSV 또는 실제 `.xlsx`를 선택합니다. 식단은 당시 영양 스냅샷, 운동은 미완료·워밍업을 포함한 실제 개별 세트/강도/휴식/메모, 체성분은 같은 날 복수 측정·실측/계산 출처·빈 항목을 유지합니다. CSV는 UTF-8 BOM/문자열 수식 중립화, XLSX는 수식이 없는 텍스트 셀·숫자·불리언·빈 셀을 사용합니다. 각 기간 내보내기는 최대 20,000행이며 오류를 성공 파일로 내려주지 않습니다.

전체 JSON 백업은 기간 선택과 별개로 19개 개인 기록 테이블과 프로필을 포함합니다. Auth 암호/계정·기기 임시 입력/타이머/테마·API 로그는 제외합니다. 최대 10MB·20,000행 범위를 넘으면 운영 DB 백업을 안내합니다. JSON 복구는 같은 계정의 빈 기록만 허용하며 자동 교체/병합을 하지 않습니다. 비밀번호·확인 문구·최신 데이터 버전을 검증한 뒤 트랜잭션으로 복구하고 ID 재발급·버전 증가·목표 버전 연속성을 통해 오래된 요청을 막습니다. PR은 다시 계산합니다. 손상/참조 오류 시 전체 취소하고 동일 백업 재시도는 완료 이력으로 중복 저장하지 않습니다. CSV/Excel은 앱 복구 형식이 아니며 JSON 파일도 암호화·서명되지 않았습니다. 안전하게 보관하세요.

**삭제·탈퇴:** 비밀번호를 재확인하고 정확한 확인 문구를 입력해야 합니다. DB에서도 2분 이내 password 인증을 요구하며 사용자 ID는 인증 주체에서만 결정합니다. 내 기록 전체 삭제는 음식·식단·운동·루틴·측정·컨디션·목표를 지우고 계정/프로필을 유지합니다. 탈퇴는 Auth 사용자와 모든 개인 기록을 삭제하고 세션을 종료합니다. 다른 사용자 기록은 영향을 받지 않습니다. 탈퇴 후 새 계정으로 앱 JSON 복구는 제공하지 않습니다. 서버 백업의 보존/삭제 정책은 운영자가 별도 안내해야 합니다.

**공개 가입:** 기본값 `FITLOG_PUBLIC_SIGNUP=false`와 Supabase Auth 가입 차단을 유지합니다. 공개 전환에는 앱 플래그·Supabase Allow new users to sign up·실제 HTTPS `FITLOG_TERMS_URL`/`FITLOG_PRIVACY_URL`·서비스 `FITLOG_APP_ORIGIN`이 필요합니다. `NEXT_PUBLIC_HCAPTCHA_SITE_KEY`를 사용하는 경우 Supabase Auth CAPTCHA도 설정하세요. 이메일 인증/SMTP·동의 정책·발송 제한은 운영 환경에서 검증해야 합니다. 가입 확인 템플릿은 `/auth/confirm?token_hash=…&type=signup`을 사용할 수 있으며 기존 invite/recovery 경로를 유지했습니다. 회원 비밀번호는 12자 이상이며 기존 계정 로그인 규칙은 유지합니다.

**보안·일관성:** 새 POST 경로는 Origin과 서비스 호스트를 검증하고 입력/파일 크기를 서버에서 제한합니다. 내보내기는 인증·no-store·다운로드 응답을 사용합니다. private RPC/보호 테이블의 직접 변경을 차단하고 기존 변경 RPC·직접 테이블 쓰기에 사용자별 잠금/변경 버전과 유효 DB 쓰기 제한을 추가했습니다. 사용자별 고정 제한: 바코드 12회/분, 사진 3회/분, 내보내기 10회/분, 복구 6회/시간, 삭제 5회/시간, 앱 및 유효 DB 쓰기 600회/분. Open Food Facts 외부 호출은 서버 전체 최근 60초 12회로 제한합니다. 실패한 DB 트랜잭션은 롤백하므로 모든 직접 실패 요청을 계수하는 전역 방화벽은 아닙니다. 공개 전 WAF/공유 IP 제한을 추가해야 합니다.

설치 아이콘/manifest/서비스 워커를 유지하고 지원 브라우저 설치 버튼·iOS 안내를 제공합니다. 카메라 라이브러리는 클릭 시 동적으로 로드하며 이미지 전처리와 XLSX 생성은 서버에서 처리합니다. 로딩/오류 경계·네트워크 상태·저장/충돌 상태를 표시하고 연결/화면 복귀 시 서버 기록을 다시 확인합니다. 기존 운동 임시 입력의 CAS 충돌/재시도를 유지하며 새 오프라인 식단/사진/백업 큐는 만들지 않았습니다. 개인정보 페이지를 오프라인 캐시하지 않습니다.
